# 页面形态模式库

## 为什么值得先给形态起名字

命名是设计资产。有了名字，讨论才能从"那个左边有菜单的页面"变成"这个应该用主从模式吧"——一句话省掉十分钟解释。

更重要的是：**名字定了，判定标准就定了**。团队吵的往往不是审美，而是"我们说的是不是同一个东西"。

形态分两类，不要混：

- **布局形态**：页面的骨架长什么样。一个页面只属于一种主形态。
- **交互模式**：行为怎么发生。可以和任意布局形态组合，一个页面可以同时用好几个。

## 布局形态速查

| 形态 | 一句话 | 识别特征 | 典型场景 |
|---|---|---|---|
| **专注模式** Focus | 导航常驻，单一内容区 | 全局菜单一直在 | 列表、详情、日常工作台 |
| **沉浸模式** Immersive | 隐藏全局导航，模块自持整屏 | 左上「返回主站」 | 画布编辑、建模、设置中枢 |
| **主从模式** Master-Detail | 左列表定对象，右区看内容 | 选中高亮 + 右侧换内容 | 邮件、数据源、任务详情 |
| **三栏工作台** Tri-pane | 导航/列表/内容三级并列 | 三列各自独立滚动 | IM、IDE、大型配置台 |
| **画布模式** Canvas | 空间即结构，节点可拖可连 | 网格背景、连线、缩放 | 工作流、血缘、看板布局 |
| **分栏对照** Split | 两屏并置，必然要比较 | 中间分隔条、可拖拽 | diff、新旧对比、翻译 |
| **看板模式** Board | 列 = 状态，卡片 = 对象 | 横向多列、拖拽换列 | 任务流转、审批流 |
| **向导模式** Wizard | 分步收集，一步一决策 | 步骤条 + 上一步/下一步 | 初始化、复杂创建 |
| **仪表盘模式** Dashboard | 指标 + 图表网格 | 卡片网格、等宽栅格 | 概览、监控 |
| **流式控制台** Console | 追加日志，自动跟随 | 时间戳行、自动滚到底、可暂停 | 运行日志、构建输出、SSE |
| **阅读模式** Reader | 长文为主，弱化导航 | 单列窄栏、目录吸顶 | Wiki、规则、帮助 |

## 五个最容易被误用的形态

### 1. 专注模式 Focus Mode

**定义**：全局菜单常驻左侧，右侧单一内容区。导航始终可见，随时可切到别的模块。

**识别**：全局菜单在，右侧内容区滚动，顶栏有「最近访问」。

**代码落点**：普通路由，不声明 `immersive`，壳层保留全局菜单。

**何时别用**：模块内部有 2 个以上并列子页却硬塞进页内 Tab——入口不可直达、返回路径消失，用户会在 Tab 之间迷失。

**避免说法**：「二级菜单」「主菜单页」。

---

### 2. 沉浸模式 Immersive Mode

**定义**：进入后隐藏全局菜单，模块自持整屏；画布或编辑区是绝对主角，退出统一走「返回主站」。

**识别**：全局菜单消失，左上角有返回入口，模块自己管左栏。

**代码落点**：路由 `meta.immersive`。两种子形态：
- `shell`——壳层渲染模块左栏（系统设置、智能问数）
- `inline`——页面自持左栏（工作流编辑、血缘画布）

**何时别用**：内容其实只有一个表格、没有编辑态。为了"看起来高级"把普通列表做成沉浸，用户会找不到回主菜单的路。

**避免说法**：「弹窗」「抽屉」「全屏弹窗」——它是可深链、可刷新的整屏路由态，不是覆盖层。

> **这对词被误用两年。** 旧代码注释把沉浸模式叫成「专注模式」，于是新人以为"专注"指全屏，在常规页上加了全屏逻辑——而按正名，"专注"恰恰是那个**不**全屏的形态。
> 处理办法：旧说法进 `aliases` 保留映射，不作为正名使用。这是 `avoid` 字段存在的唯一理由。

---

### 3. 主从模式 Master-Detail

**定义**：左侧是对象列表，右侧是当前选中对象的详情。选中即切换，不跳页。

**识别**：左列有选中态高亮，右区标题随选中项变化，URL 里带着选中项的 id。

**代码落点**：列表与详情共享父级状态；选中项写进 query（`?id=xxx`），刷新能还原。

**何时别用**：
- 详情需要占满整屏去编辑（该用沉浸模式）
- 两个对象要长期并排比较（该用分栏对照）
- 列表项本身就是内容（如消息流，右区是输入框）

**常见坑**：选中态存在组件 state 而不是 URL —— 分享链接给同事，对方看到的是默认第一项。

---

### 4. 画布模式 Canvas

**定义**：空间位置即语义。节点可拖拽，连线表达依赖，缩放平移是基本操作。

**识别**：网格背景、小地图或缩放控件、拖拽后布局被记住。

**代码落点**：布局只存坐标；**连线由节点依赖派生，不单独建边表**——否则会出现"有边没依赖"的状态分裂。

**何时别用**：对象之间关系是一对一线性流程时，用向导或列表更省心。画布的学习成本要靠"空间关系有价值"来还。

---

### 5. 流式控制台 Console

**定义**：新内容追加在末尾，视口自动跟随；用户可以暂停跟随去翻历史。

**识别**：等宽字体、时间戳、自动滚到底、出现"暂停跟随"按钮。

**代码落点**：SSE/WebSocket 追加到数组；只在用户位于底部时才自动滚动（否则会抢走用户正在看的位置）。

**何时别用**：内容是结构化的表格数据（那该用表格 + 分页），或者需要长时间回看历史（该用日志检索页）。

**常见坑**：无条件 `scrollTop = scrollHeight`，导致用户往前翻的时候被拽回去。

## 交互模式速查

这些是行为，和布局正交，可以叠加。

| 模式 | 一句话 | 判定标准 | 何时别用 |
|---|---|---|---|
| **渐进披露** | 先给结论，细节按需展开 | 首屏只出现 80% 场景需要的信息 | 关键信息藏在二级里（用户永远不会点） |
| **就地编辑** | 在展示位置直接改 | 点文字变输入框，失焦保存 | 字段多、需要校验联动（该进弹层） |
| **乐观更新** | 先改界面，再发请求 | 操作立即生效，失败回滚 + 提示 | 破坏性操作、涉及金额 |
| **撤销优于确认** | 先执行，给 5 秒后悔 | toast 里带「撤销」 | 不可逆操作（删除整个库） |
| **命令面板** | 一个入口找所有功能 | `Ctrl+K` 唤起 | 功能少于 10 个（不如直接摆出来） |
| **批量操作条** | 选中后才出现操作 | 勾选 ≥1 项时浮出、显示选中数 | 列表不支持多选 |
| **危险操作证据化** | 要求输入名称才继续 | 输入框要手打资源名 | 普通删除（过度设计） |
| **四态齐全** | 空/加载/错/无权限 | 四种都有独立视觉 | 永不失败的内页（几乎不存在） |
| **骨架先于转圈** | 用形状占位而非 spinner | 首屏有布局占位 | 局部刷新（用行内 loading） |

## 选型决策树

按顺序问，第一个命中的就是答案：

```
1. 是编辑一个复杂对象（画布/表单/建模），需要整屏？
   → 沉浸模式

2. 模块内有 ≥2 个并列子页（独立路由或 ?tab=）？
   → 沉浸模式（shell）—— 子页塞进页内 Tab 会让入口不可直达

3. 列表 + 点开看详情，两者要频繁切换？
   → 主从模式（选中项写进 URL）

4. 两个东西要一直并排比较？
   → 分栏对照

5. 核心是状态流转（待办→进行→完成）？
   → 看板模式

6. 首次使用、一次性配置、步骤有依赖？
   → 向导模式

7. 看整体数字与趋势，不需要逐个操作？
   → 仪表盘模式

8. 输出是持续追加的日志/事件流？
   → 流式控制台

9. 以上都不是
   → 专注模式（默认，别过度设计）
```

**决策树的意义是让"默认"变成专注模式。** 大部分页面不需要特殊形态，特殊形态是成本。

## 组合规则

- 一个页面**只有一个主形态**。两个主形态叠加 = 谁都不是。
- 交互模式可以叠加，但**同屏主动作只有一个**（primary action）。
- 沉浸模式内部仍可用主从、画布、控制台；但不能再嵌一个沉浸。

## 反模式

| 反模式 | 为什么错 | 正确做法 |
|---|---|---|
| 沉浸页里再开一个全屏弹窗 | 用户不知道自己在第几层，返回路径断裂 | 用抽屉或页内面板 |
| 普通列表做成沉浸模式 | 失去跨模块导航，成本换不到收益 | 专注模式 |
| 主从模式右区又是列表 | 两次"选择"，认知负担翻倍 | 改成三栏，或右区直接给详情 |
| 画布模式却只有 3 个节点 | 空间成本高于信息收益 | 用向导或列表 |
| 控制台无条件自动滚动 | 用户翻历史时被拽回底部 | 只在贴底时跟随 |
| 每个页面自定义形态 | 术语失效，新人靠猜 | 从模式库里选，不新增 |

## 怎么往项目里加新形态

不是先写代码，是先写词条：

1. 在 `rules.json` 的 `pageModes` 加一条，**五个字段都要填**：`definition` / `signal` / `codeHint` / `avoid` / `appliesTo`。
2. 问自己：能不能被现有形态覆盖？能，就不要加（形态越多，共同语言越弱）。
3. 场景实例少于 3 个，不要立为新形态——它是某个形态的变体。
4. 加完，规则页与导出的 AI 上下文自动出现它，不用改别的地方。

## 验收

- [ ] 团队里说"这个用主从模式"，所有人都能画出同一个骨架
- [ ] 每个形态都有 `signal`（肉眼可辨）和 `codeHint`（代码可定位），而不是只有定义
- [ ] 每个形态都写了 `avoid`，且能举出一个真实误用案例
- [ ] 形态数量 ≤ 8 种布局 + ≤ 10 种交互，超了说明在做分类学不是在做产品
- [ ] 新页面能对着决策树在 30 秒内定下形态

# 规则页（项目规则 + 术语）

## 这一页真正解决的问题

不是"写一份规范文档"，而是：**换一个 AI / 换一个人接手时，不用重新解释一遍术语和禁令。**

所以它的第一读者是 agent，第二读者才是人。设计判据只有一条：

> 把导出的 Markdown 交给一个没读过代码的 agent，它能不能正确使用"专注模式"这个词，并且不去做被禁止的事？

做不到，就是词条写得不够。

## 两个区块，不能混

| 区块 | 内容 | 为什么单列 |
|---|---|---|
| **页面形态 / 术语** | 用户视角的工作形态叫什么、指什么、怎么一眼认出、不要叫什么 | 形态是"共同语言"，不是约束；混进规则列表会被当成可选项 |
| **规则清单** | 分类 + 分级 + 出处 | 要能被门禁脚本核对 |

## 术语词条的结构（照抄这个字段集）

```jsonc
{
  "key": "focus",                  // 稳定标识，代码里引用它
  "name": "专注模式",               // 正名，唯一可用叫法
  "english": "Focus Mode",
  "aliases": ["常规页", "主菜单模式"],   // 旧称/行业叫法 —— 只用于听懂历史讨论
  "definition": "全局菜单栏常驻左侧，右侧为单一内容区……",
  "appliesTo": ["工作台", "数据源", "采集任务"],   // 哪些页面属于这个形态
  "signal": "240px 全局菜单常驻 + 右侧内容区滚动 + 顶栏「最近访问」",  // 一眼认出的特征
  "codeHint": "普通路由，不声明 immersive，壳层保留全局菜单",
  "avoid": ["不要叫「二级菜单」", "不要把全屏画布塞进常规页"]     // 最容易混的说法
}
```

四个字段各有不可替代的作用，缺一个就失效：

- `definition` 不够 —— 定义往往是抽象的，"右侧是单一内容区"这种话谁都能往自己项目上套。
- 必须配 `signal`（看得见的特征）和 `codeHint`（代码落点），才能从"人看到的"和"代码里的"两头对上。
- 必须配 `avoid`，因为**误解通常来自近义词**，不来自一无所知。

## 真实案例：一个词被误用两年

来源项目里最典型的一次事故：

| | 专注模式 Focus Mode | 沉浸模式 Immersive Mode |
|---|---|---|
| 形态 | 全局菜单常驻 + 右侧单一内容区 | 全局菜单隐藏 + 模块自持整屏 |
| 识别 | 240px 菜单一直在 | 左上「返回主菜单」 |
| 适用 | 工作台、数据源、任务运维 | 工作流编辑、看板编辑、智能问数、**系统设置** |
| 代码 | 普通路由 | `meta.immersive = 'shell' \| 'inline'` |
| **旧称陷阱** | 曾被叫作"常规页" | **旧代码注释里被叫作"专注模式"** |

后果：新人读注释以为"专注模式"指全屏工作区，于是在常规页上加了全屏逻辑；而按正名，"专注模式"恰恰是那个**不**全屏的形态。

处理办法不是删掉旧说法，而是把它放进 `aliases`，并明确标注"旧代码注释里的『专注模式』实指沉浸模式"。**保留旧称做映射，不作为正名使用。**

这条经验直接进 `avoid` 字段：`"不要叫「弹窗/抽屉/全屏弹窗」—— 它是可深链、可刷新的整屏路由态"`。

## 规则条目结构

```jsonc
{
  "id": "C-05",                   // 前缀=分类，数字=序号，永不复用
  "category": "component",        // visual | motion | component | engineering
  "severity": "must",             // must 必须 / should 建议（should 不阻断构建）
  "title": "新增共享组件先登记",
  "summary": "新增共享组件必须登记到「设置 → 组件」注册表后才算完成。",
  "detail": "注册表会扫描真实目录，未登记的组件会在页面上直接标出来。",
  "source": "keel/components.json · scripts/console-check.mjs"   // 可核对
}
```

四个分类建议保持稳定，别自定义一堆：

| 分类 | 管什么 | 典型条目 |
|---|---|---|
| `visual` | 颜色/字体/字号/圆角/主题 | 只用令牌，不裸写 px；主题切换只动令牌层 |
| `motion` | 动效归属与属性白名单 | 只允许 transform/opacity/box-shadow；尊重 reduced-motion |
| `component` | 组件边界、复用、登记 | 业务视图不直连组件库；跨域组件上移共享层；新增先登记 |
| `engineering` | 权限、接口信封、配置来源、禁演示数据 | 禁止演示数据；配置只有一个活源；**四件套必须自动更新** |

`source` 字段不是装饰：规则被违反时，人和脚本都要能顺着它找到该改的文件。**没有 source 的规则，一个月后没人敢执行。**

必须有一条"元规则"兜住四件套本身，否则它自己会烂掉：

> **E-05 规则、组件、接口文档、Wiki 必须自动更新** —— 这四类不允许人肉另存一份：代码或源文件一变，页面必须自动反映最新事实。改动后无需额外"同步文档"步骤即可见，任何手写副本都视为违规。

## AI 上下文导出

页面必须有「复制 AI 上下文」按钮，输出结构固定的 Markdown：

```markdown
# <项目名> 项目规则与术语

> 版本 2026-10-23 · 由 keel/rules.json 生成，单一真相源。

## 一、页面形态
### 专注模式（Focus Mode）
<definition>
- 识别特征：<signal>
- 适用页面：<appliesTo 用、连接>
- 代码落点：<codeHint>
- 旧称/同义：<aliases>
- 避免说法：<avoid 用；连接>

## 二、规则清单
### 视觉与令牌
- **[必须] V-01 文字对比度不低于 4.5:1**：<summary><detail>
```

三条要求：

1. **版本号必须写**，放在 `rules.json` 里（`version: "2026-10-23"`），exprompt 时能判断对方拿的是不是旧版。
2. **用中文标签**（"必须/建议"而不是 must/should），因为读它的是自然语言模型不是编译器。
3. **每类前先出分类描述**，让 agent 知道这一类管什么、不管什么。

## 维护纪律

- 新增/修改规则**只改 `rules.json`**，页面里不写任何文案。
- 旧称只进 `aliases`，不拿来当正名，也不删除（删了就没人懂历史讨论）。
- `id` 永不复用；废弃规则标 `"deprecated": true` 保留，不要直接删（否则老 PR 引用会断）。
- 规则数量控制在 **20～40 条**。超过 40 条，人会选择性忽略；这时该做的是合并同类项，不是继续加。

## 页面骨架

```
Hero（版本号 + 规则总数 + 「复制 AI 上下文」按钮）
├── 01 页面形态   词条卡片：正名 / 定义 / 识别特征 / 代码落点 / 旧称 / 避免说法
└── 02 规则清单   分类筛选 → 规则卡片：ID + 分级 + 标题 + 摘要 + 出处
```

不做的：不要做树形折叠目录（规则不多，折叠反而难扫）；不要做搜索框（40 条以内不需要）。

## 验收

- [ ] 随手改一条规则的 `title`，刷新页面就变了，没有第二步
- [ ] 导出的 Markdown 里，"专注模式"和"沉浸模式"的区别，一个没读过代码的 agent 能看懂
- [ ] 每条规则都有 `source`，点开能找到对应文件
- [ ] 页面上不存在任何一段与 JSON 内容不一致的手写文案
- [ ] 规则里有一条专门约束"四件套必须自动更新"

# 规则页（项目规则 + 术语）

## 这一页真正解决的问题

不是"写一份规范文档"，而是：**换一个 AI / 换一个人接手时，不用重新解释一遍术语和禁令。**

所以它的第一读者是 agent，第二读者才是人。设计判据只有一条：

> 把导出的 Markdown 交给一个没读过代码的 agent，它能不能正确使用"专注模式"这个词，并且不去做被禁止的事？

做不到，就是词条写得不够。

## 三个区块，不能混

| 区块 | 内容 | 为什么单列 |
|---|---|---|
| **页面形态** | 用户视角的工作形态叫什么、指什么、怎么一眼认出、不要叫什么 | 形态是"共同语言"，不是约束；混进规则列表会被当成可选项 |
| **术语表** | 一切共用的词：单一真相源、响应信封、空态、令牌、壳层、未登记组件、降级…… | 同一个词被理解成两个意思，比没人定义更糟。定义一次，之后就靠它对齐 |
| **规则清单** | 分类 + 分级 + 出处 | 要能被门禁脚本核对 |

形态与术语是同一类东西（都是"共同语言"），字段要求完全一致：**正名 + 定义 + 识别信号 + 代码落点 + 不要怎么叫**。区别只是形态描述空间（页面长什么样），术语描述词（我们怎么称呼一件事）。

## 默认库给到什么程度

模板自带的是一套**能直接用的起点**，不是两条示例：

| 区块 | 条数 | 覆盖 |
|---|---|---|
| 页面形态 | 4 | 专注 / 沉浸 / 主从 / 看板 |
| 术语表 | 8 | 单一真相源、可见性边界、响应信封、空态、令牌、壳层、未登记组件、降级 |
| 规则清单 | 15 | 六个分类，每个分类至少 1 条 must |

但**`source` 全是示例路径**。落地第一件事就是逐条替换成你项目里的真实文件——写不出真实路径的规则就删掉，留着只会让人不敢执行。

## 术语词条的结构（照抄这个字段集）

```jsonc
{
  "key": "focus",                  // 稳定标识，代码里引用它
  "name": "专注模式",               // 正名，唯一可用叫法
  "english": "Focus Mode",
  "aliases": ["常规页", "主菜单模式"],   // 旧称/行业叫法 —— 只用于听懂历史讨论
  "definition": "全局菜单栏常驻左侧，右侧为单一内容区……",
  "appliesTo": ["工作台", "数据源", "采集任务"],   // 哪些页面属于这个形态
  "signal": "240px 全局菜单常驻 + 右侧内容区滚动 + 顶栏「最近访问」",  // 一眼认出的特征
  "codeHint": "普通路由，不声明 immersive，壳层保留全局菜单",
  "avoid": ["不要叫「二级菜单」", "不要把全屏画布塞进常规页"],     // 最容易混的说法
  "status": "confirmed"            // confirmed | draft，见下节
}
```

术语表条目少两个字段（`appliesTo` 只对形态有意义），其余一样。

四个字段各有不可替代的作用，缺一个就失效：

- `definition` 不够 —— 定义往往是抽象的，"右侧是单一内容区"这种话谁都能往自己项目上套。
- 必须配 `signal`（看得见的特征）和 `codeHint`（代码落点），才能从"人看到的"和"代码里的"两头对上。
- 必须配 `avoid`，因为**误解通常来自近义词**，不来自一无所知。

## 规则自举：让 agent 从代码里整理出候选

这部分是"规则页"和"手写规范文档"的分水岭。人不会主动写规范，但 agent 可以先把代码里**已经存在的模式**整理成候选，人只需要点头或删掉。

四步，顺序不能变：

**① 扫事实**（只读，不改任何文件）

| 找什么 | 从哪找 | 提炼成 |
|---|---|---|
| 目录分层与引用方向 | `src/` 目录结构、import 关系 | 组件边界类规则（C-xx） |
| 页面形态特征 | 路由 meta、壳层是否隐藏菜单 | pageModes 词条 |
| 主题与令牌 | `theme/`、`*.css`、颜色/字号字面量 | 视觉类规则（V-xx） |
| 接口封装 | 响应包装函数、错误处理中间件 | 工程类规则（E-xx） |
| 反复出现的注释与 README 段落 | 全仓 grep「不要」「禁止」「必须」 | 规则候选原文 |

**② 写成候选**，每条必须带 `evidence`：

```jsonc
{
  "id": "C-06",
  "title": "异步状态统一走 useAsync",
  "status": "draft",
  "evidence": ["src/shared/useAsync.ts:1", "src/views/datasource/List.vue:42"],
  "confidence": "high"
}
```

`evidence` 是硬要求——**没有出处的候选就是幻觉**。`confidence` 写 `high|medium|low`，低的优先让人先看。

**③ 人确认**：页面上 draft 条目带「待确认」标记，逐条点「采纳 / 删掉 / 改完再采纳」。采纳 = `status` 改成 `confirmed`。

**④ 只有 `confirmed` 进 AI 上下文导出。** draft 一律不导出——把 AI 猜的东西当团队规范发出去，比没有规范更糟。

体检脚本的 `RULE-05` 会盯这一条：draft 缺 `evidence` 直接 warn。

**不要做的事**：不要让 agent 自动把候选改成 confirmed；不要因为它读到了一个模式就认为这是"团队决定"。它只是把已存在的事实说了一遍，判断权在人。


## 真实案例：一个词被误用两年

来源项目里最典型的一次事故：

| | 专注模式 Focus Mode | 沉浸模式 Immersive Mode |
|---|---|---|
| 形态 | 全局菜单常驻 + 右侧单一内容区 | 全局菜单隐藏 + 模块自持整屏 |
| 识别 | 240px 菜单一直在 | 左上「返回主菜单」 |
| 适用 | 工作台、数据源、任务运维 | 工作流编辑、看板编辑、智能问数、**系统设置** |
| 代码 | 普通路由 | `meta.immersive = 'shell' \| 'inline'` |
| **旧称陷阱** | 曾被叫作"常规页" | **旧代码注释里被叫作"专注模式"** |

后果：新人读注释以为"专注模式"指全屏工作区，于是在常规页上加了全屏逻辑；而按正名，"专注模式"恰恰是那个**不**全屏的形态。

处理办法不是删掉旧说法，而是把它放进 `aliases`，并明确标注"旧代码注释里的『专注模式』实指沉浸模式"。**保留旧称做映射，不作为正名使用。**

这条经验直接进 `avoid` 字段：`"不要叫「弹窗/抽屉/全屏弹窗」—— 它是可深链、可刷新的整屏路由态"`。

## 规则条目结构

```jsonc
{
  "id": "C-05",                   // 前缀=分类，数字=序号，永不复用
  "category": "component",        // visual | motion | component | engineering
  "severity": "must",             // must 必须 / should 建议（should 不阻断构建）
  "title": "新增共享组件先登记",
  "summary": "新增共享组件必须登记到「设置 → 组件」注册表后才算完成。",
  "detail": "注册表会扫描真实目录，未登记的组件会在页面上直接标出来。",
  "source": "keel/components.json · scripts/console-check.mjs"   // 可核对
}
```

四个分类建议保持稳定，别自定义一堆：

| 分类 | 管什么 | 典型条目 |
|---|---|---|
| `visual` | 颜色/字体/字号/圆角/主题 | 只用令牌，不裸写 px；主题切换只动令牌层 |
| `motion` | 动效归属与属性白名单 | 只允许 transform/opacity/box-shadow；尊重 reduced-motion |
| `component` | 组件边界、复用、登记 | 业务视图不直连组件库；跨域组件上移共享层；新增先登记 |
| `engineering` | 权限、接口信封、配置来源、禁演示数据 | 禁止演示数据；配置只有一个活源；**四件套必须自动更新** |

`source` 字段不是装饰：规则被违反时，人和脚本都要能顺着它找到该改的文件。**没有 source 的规则，一个月后没人敢执行。**

必须有一条"元规则"兜住四件套本身，否则它自己会烂掉：

> **E-05 规则、组件、接口文档、Wiki 必须自动更新** —— 这四类不允许人肉另存一份：代码或源文件一变，页面必须自动反映最新事实。改动后无需额外"同步文档"步骤即可见，任何手写副本都视为违规。

## AI 上下文导出

页面必须有「复制 AI 上下文」按钮，输出结构固定的 Markdown：

```markdown
# <项目名> 项目规则与术语

> 版本 2026-10-23 · 由 keel/rules.json 生成，单一真相源。

## 一、页面形态
### 专注模式（Focus Mode）
<definition>
- 识别特征：<signal>
- 适用页面：<appliesTo 用、连接>
- 代码落点：<codeHint>
- 旧称/同义：<aliases>
- 避免说法：<avoid 用；连接>

## 二、术语表
### 单一真相源（Single Source of Truth）
<definition>
- 识别特征：<signal>
- 代码落点：<codeHint>
- 避免说法：<avoid 用；连接>

## 三、规则清单
### 视觉与令牌
- **[必须] V-01 文字对比度不低于 4.5:1**：<summary><detail>
```

三条要求：

1. **版本号必须写**，放在 `rules.json` 里（`version: "2026-10-23"`），exprompt 时能判断对方拿的是不是旧版。
2. **用中文标签**（"必须/建议"而不是 must/should），因为读它的是自然语言模型不是编译器。
3. **每类前先出分类描述**，让 agent 知道这一类管什么、不管什么。

第四条是 2.x 新增的：**只导出 `status: "confirmed"` 的条目**。draft 是候选，不是规范；把候选发给 agent，等于让它把猜测当事实执行。

## 维护纪律

- 新增/修改规则**只改 `rules.json`**，页面里不写任何文案。
- 旧称只进 `aliases`，不拿来当正名，也不删除（删了就没人懂历史讨论）。
- `id` 永不复用；废弃规则标 `"deprecated": true` 保留，不要直接删（否则老 PR 引用会断）。
- 规则数量控制在 **20～40 条**。超过 40 条，人会选择性忽略；这时该做的是合并同类项，不是继续加。
- **术语条数不设上限**，但一条术语只要有两个人理解不同，就说明 `avoid` 没写够。补 `avoid`，不要加新词。
- 候选条目（`draft`）超过 10 条没处理，说明第 ③ 步没人做——要么排期确认，要么整批删掉。攒着不处理比没有候选更糟。

## 页面骨架

```
Hero（版本号 + 形态/术语/规则三个计数 + 「复制 AI 上下文」按钮）
├── 01 页面形态   词条卡片：正名 / 定义 / 识别特征 / 代码落点 / 旧称 / 避免说法
├── 02 术语表     同一套卡片，少「适用页面」一行；右上角显示 draft 的「待确认」标记
└── 03 规则清单   分类筛选 → 规则卡片：ID + 分级 + 标题 + 摘要 + 出处
```

三块共用一张卡片组件，别为形态和术语各写一套——字段几乎一样，两套必然长歪。

draft 条目的处理入口就在卡片右上角：**采纳 / 删掉**。不要在页面上做批量「一键采纳」——那是把判断权交回给机器。

不做的：不要做树形折叠目录（规则不多，折叠反而难扫）；不要做搜索框（40 条以内不需要）。

## 验收

- [ ] 随手改一条规则的 `title`，刷新页面就变了，没有第二步
- [ ] 导出的 Markdown 里，"专注模式"和"沉浸模式"的区别，一个没读过代码的 agent 能看懂
- [ ] 术语表至少覆盖项目里最容易叫岔的 6 个词，每个都有 `avoid`
- [ ] 每条规则都有 `source`，点开能找到对应文件
- [ ] 让 agent 扫一遍代码，它能产出带 `evidence` 的 draft 候选，且页面上能逐条采纳
- [ ] 导出的 Markdown 里找不到任何 draft 条目
- [ ] 页面上不存在任何一段与 JSON 内容不一致的手写文案
- [ ] 规则里有一条专门约束"四件套必须自动更新"（E-05）

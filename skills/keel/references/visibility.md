# 可见性边界

## 先扔掉这个问题

「现在是开发模式还是线上模式？」——这个问题没有答案，因为它默认同一个包会在两副面孔之间切换。

真正要问的是三句：

1. 这东西**该不该出现在这个产物里**？
2. **该不该被这个人打开**？
3. 同一个页面里，**哪些字段不能给他**？

三个问题、三个层次、三种修法。混在一起修，就会出现「加了权限，但源码路径还躺在 bundle 里」这种事故。

**它不是一个状态。** 不显示、不切换、没有角标、没有 `?mode=dev`。它在构建配置和服务端鉴权里，跑起来就改不了——这正是它的价值。

## 为什么「开发模式 / 线上模式」是错的设计

这个技能 1.x 用过它，2.0 删掉了。三个理由，每条都是真实代价：

| 问题 | 后果 |
|---|---|
| 它假设一个包有两种形态 | 桌面端安装包装上客户电脑后，不会因为登录管理员就变成 web 端。决定形态的是构建配置，不是运行时变量 |
| 有开关就有忘记关的开关 | 忘关的后果不由你承担，由客户承担。角标只是让你「更容易发现忘了关」，不是让你不会忘 |
| 「模式」这个词会把人骗到前端 | 本该在构建期剔除的页面，被写成 `v-if`。**坏的不是这次忘了关，是下次还在前端解决** |

第三条最贵。一个词决定了你去哪一层修问题。

## 三层

从上往下定，顺序不能反。

| 层 | 问题 | 修在哪 | 判定方式 | 典型 |
|---|---|---|---|---|
| **产物层** | 进不进这个包？ | 构建配置（多入口 / 路由表分流 / 打包排除） | 解包或搜产物，搜不到就是没有 | 桌面端里的设置页、客户私有化部署里的内部 Wiki |
| **身份层** | 谁能打开它？ | 服务端鉴权（一处中间件 / 一条守卫） | 换个没权限的账号请求，返回 401/404 | 接口文档、审计日志、组件注册表 |
| **字段层** | 哪些字段不能给这个人？ | 序列化白名单（响应组装处） | 抓响应体，字段不在里面 | 源码路径、错误堆栈、内部 id、别家租户数据 |

三层的分界只有一句话：**越往下越便宜，越便宜越不可靠。**

字段层改一行代码，但它挡不住 DevTools；身份层要一次服务端改动，能挡住直接请求；产物层要动构建配置，但它是唯一「泄露后无法回收」的解法。

## 四问（照抄进项目，逐条写答案）

四行字就够，不必是文件。写在 `keel/console.config.json`、`docs/visibility.md`、README 的一节，都行——只要**可定位**。

1. **这个项目最终以哪几种形态交付？** web 站 / 桌面安装包 / CLI / 客户私有化部署 / 只在内网跑。几种就是几个产物。
2. **每种形态里，设置页和四件套该不该存在？** 逐一对上，不许写「视情况」。
3. **该存在的，谁能打开？** 给一个身份名，不写「内部人」这种模糊说法。「登录后的员工」和「登录后的管理员」是两个答案。
4. **误展示的最坏后果是什么？** —— 唯一决定「该用多大劲」的问题。

## 力度按第 4 问定

| 最坏后果 | 修在哪层 | 做法 |
|---|---|---|
| 只是不好看、显得乱 | 字段层 | 前端不渲染。够了，别过度设计 |
| 泄露内部结构，读者是团队之外的人 | 身份层 | 服务端鉴权。前端拿不到数据就没得显示 |
| 泄露后收不回来（进了别人磁盘、被搜索引擎收了） | 产物层 | 构建期剔除。包里根本不存在这个路由 |

一句硬话：**能在构建期解决的，不要留给运行时。**

「不好看」就该只做字段层。给未登记组件告警条加一套服务端鉴权，是把成本花在没人受影响的威胁上——这类过度设计会让人下次连该做的也不做了。

## 落点自由

技能不规定文件名，因为项目形态本来就千人千面（Electron + 后台、纯 web 带 RBAC、只在内网跑的运维台，答案完全不同）。只要求两件事：

- **可定位** —— 新来的 agent 能在一个已知位置找到这份声明。写在 `console.config.json` 的 `visibility` 段、`docs/visibility.md`、或 README 里一节都可以，但只能有一处。
- **可追溯** —— 每条「不给看」的决定都能回答「如果给看了会怎样」。答不出来，说明这条是抄来的，不是在防什么。

### 三种典型项目写出来长什么样

**A. 桌面端 + web 后台，同一个前端仓库**

| 形态 | 四件套 | 谁能开 | 最坏后果 → 修在哪 |
|---|---|---|---|
| 桌面安装包 | 不存在 | — | 客户在安装目录里翻到接口文档 → **产物层** |
| web 后台 | 存在 | 登录员工 | 员工看到未登记组件告警条 → 字段层 |

**B. 纯 web，自带登录与 RBAC**

| 形态 | 四件套 | 谁能开 | 最坏后果 → 修在哪 |
|---|---|---|---|
| web 站 | 存在（`settings:view`） | 管理员 | 普通账号拿到 `/openapi.json` 摸清全部接口 → **身份层** |

这一种最容易被写错：项目只有一个产物，于是所有问题都被丢到字段层用 `v-if` 解决。**单产物不等于单层。**

**C. 只在内网跑的运维台**

| 形态 | 四件套 | 谁能开 | 最坏后果 → 修在哪 |
|---|---|---|---|
| 内网部署 | 全部存在 | 有内网访问权的人 | 无（内网边界就是边界） |

这一种可以只写一行「不做边界，理由：内网」。**写明「不做」也是答案**，比假装做了要好。

## 各层的最小骨架

只给「该在哪层动」，写法随栈替换。

**产物层** —— 让不该存在的代码进不了入口。多入口、路由表分流、打包 externals 都行：

```ts
// 桌面端入口根本不 import web 专属路由 —— 不是导入后再过滤
const routes = [
  ...coreRoutes,
  ...(import.meta.env.VITE_TARGET === 'web' ? webOnlyRoutes : []),
]
```

**身份层** —— 唯一的门在服务端，且只有一处：

```py
# 前端隐藏只是顺手，不是防线。挡人靠这一行
@router.get("/admin/settings", dependencies=[Depends(require("settings:view"))])
```

**字段层** —— 用白名单，不要黑名单：

```ts
// ✅ 白名单：新增字段默认不出去，加错也只是少给了
const toPublic = (c: Component) => ({ name: c.name, purpose: c.purpose })

// ❌ 黑名单：每加一个敏感字段都得记得回来补一行，一定漏
const toPublic = ({ sourcePath, ...rest }: Component) => rest
```

## 反模式

| 反模式 | 为什么错 |
|---|---|
| 用 `NODE_ENV` / `import.meta.env.DEV` 决定「要不要给用户看内部事实」 | 它表达构建方式，不表达读者身份。同一个 prod 包要给两种人看时，它给不出答案 |
| 界面上放模式角标 | 需要角标，说明设计没解决问题：形态是构建期定的，它就不该变；如果它会变，依据应该是身份，不是一个自选开关 |
| `?mode=dev` 之类 URL 升权 | 忘记关的开关 + 可被扫到的入口 = 信息泄露。加 `canElevate` 只是把它变成「需要登录的信息泄露」 |
| 前端 `v-if` 挡接口文档 | 数据已经到浏览器了，DevTools 里一行代码就绕过去 |
| 用「是否内网 IP」判身份 | IP 会变、代理会骗。用账号 |
| 桌面端「顺手带上设置页，反正没人点」 | 包里有的东西迟早被找到，打包体积也是成本 |
| 所有问题都用字段层解决 | 单产物项目的通病。该服务端鉴权的字段，前端隐藏等于没做 |

## 验收

- [ ] 有一份边界声明，覆盖项目的每一种交付形态（几行字即可，不必是文件）
- [ ] 每条「不给看」都写了最坏后果，且修法与后果同层（好看 → 前端；内部 → 服务端；收不回 → 构建期）
- [ ] 桌面端 / 私有化产物里搜不到设置页路由、`openapi.json`、`docs/wiki` 字样
- [ ] 无权限身份请求接口文档，返回 401/404，而不是前端看不见
- [ ] 页面里没有任何「模式 / 形态」角标或切换开关
- [ ] 字段层用白名单导出，新增敏感字段不需要回头改黑名单
- [ ] 明确写了「不做的边界」和理由（内网、单人项目都算合法理由）

## 从 1.x 迁过来

装过旧版的话，删掉 `keel/devMode.ts`，按三层重新落一遍：

| 旧东西 | 怎么处理 |
|---|---|
| 模式角标 / `useModeBadge` | 删掉。它的信息本该由「这个包是哪个产物」回答，而那件事写在打包配置里 |
| `canElevate` / `?mode=dev` | 删掉。要「临时看一眼」就去本地跑 dev 构建，别在生产包里留后门 |
| `MODE_VISIBILITY` 矩阵 | 按「最坏后果」重新分三列，不是按 dev/prod 分两列 |
| `isDev()` 包裹的 UI | 逐条问第 4 问：不好看 → 保留并只在前端藏；内部结构 → 挪到服务端鉴权；收不回 → 挪到构建期 |

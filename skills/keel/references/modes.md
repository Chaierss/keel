# 开发模式 / 线上模式

## 一句话定义

- **开发模式（Dev Mode）**：项目对自己人透明。允许暴露内部事实——源码路径、未登记告警、未使用清单、错误堆栈、可试调的接口文档、组件 demo。目标是**协作与排障效率**。
- **线上模式（Prod Mode）**：只保留可交付事实。四件套降级为只读镜像或整体隐藏，内部路径、堆栈、调试入口一律不出现。目标是**不给外人看内部结构**。

这两个词必须在项目里只有一种含义。**它不是 `NODE_ENV`，不是用户角色，不是暗色主题，不是"体验版/付费版"。**

## 为什么必须最先定义

它决定后面三件事，定晚了就要返工：

1. **可见性** —— 四件套的哪些 tab、哪些告警块、哪些源码路径出现。
2. **写权限** —— 能不能在页面上直接改配置 / 切换 provider / 重跑任务。
3. **数据面** —— 是否允许展示 demo 数据、是否允许真实试调、错误信息要不要脱敏。

## 判定标准（三条同时满足才算"有模式"）

| 判定 | 具体形态 | 不满足的表现 |
|---|---|---|
| 单一判定点 | 全项目只有一个 `resolveMode()`，任何 UI 分支都问它 | 每个页面各写 `import.meta.env.DEV`，第 7 处永远漏 |
| 可见角标 | 界面上常驻模式标识（左下角/顶栏胶囊），hover 显示"判定来源" | 你自己都分不清现在开的是哪个模式 |
| 刷新可保持 | 模式写进 URL 或存储，刷新/分享后形态不变 | 刷新回默认，或分享链接对方看到另一套界面 |

## 判定来源与优先级

```ts
// 优先级从高到低，后者只在前者缺失时生效
1. 构建期常量      BUILD_MODE = 'dev' | 'prod'   // 打包时写死，线上包无法被翻上去
2. URL 参数        ?mode=dev                     // 必须过权限校验，否则视为无效
3. 本地存储        localStorage['app.mode']      // 开发者自选，用于本地验证线上形态
4. 默认值          构建期是 dev，产物是 prod
```

**硬约束：线上包不允许通过 URL/存储升权到开发模式，除非当前账号具备管理员权限。** 否则 `?mode=dev` 就是一个信息泄露入口。

需要"线上包里也能临时看一眼开发形态"时，正确做法是：取到管理员 token 才放行，且切换后角标变成醒目的**黄色"开发模式（临时）"**，避免忘记关。

## 可见性矩阵

把它当成一张表钉在项目里，新增 tab 先填这张表，不要临场判断。

| 内容 | 开发模式 | 线上模式 |
|---|---|---|
| 规则页 | 完整（含"未登记/待还债"提示） | 只读（隐藏内部出处路径） |
| 组件页 | 完整（demo 预览 + 未登记告警 + 未使用清单 + 源码路径） | 隐藏，或仅保留名称与用途 |
| 接口文档 | 完整 + 可试调 | 关闭（`DISABLE_DOCS=1`）或仅内网可达 |
| Wiki | 完整 + 允许打开仓库路径 | 只读渲染，隐藏"编辑源文件"指引 |
| 错误提示 | 原始 message + 堆栈 + 请求 ID | 脱敏文案 + 请求 ID |
| 调试面板 / 命令面板 | 显示 | 隐藏（或仅管理员） |
| 未登记 / 未使用 告警块 | 显示 | **必须隐藏**——这是内部债，不是给客户的 |
| 系统日志 / 审计 | 显示 | 按权限显示（与模式无关，走 RBAC） |

注意最后两行：**模式管"内部事实"，权限管"业务数据"**。两者不要混：不要因为"线上模式"就把审计日志砍掉，也不要因为"管理员"就暴露源码路径给客户演示账号。

## 实现骨架

见 `templates/devMode.ts`。核心三条：

```ts
export type AppMode = 'dev' | 'prod'

const BUILD_MODE: AppMode = (import.meta.env?.VITE_APP_MODE ?? 'dev') as AppMode

export function resolveMode(opts: { canElevate: boolean }): { mode: AppMode; source: ModeSource }
export function isDev(): boolean          // 唯一的布尔出口
export function useModeBadge(): { text, tone, hint }
```

规则：

- 业务代码只调 `isDev()`，**不读 `import.meta.env`**。
- 需要"开发模式专属 UI"的地方，用 `isDev()` 包裹，不要新增第二套布局。
- 打包时把 `BUILD_MODE` 写死，线上包里这个常量就是 `'prod'`，不依赖运行时环境。
- 切换模式**必须整页刷新**语义（或重新拉取数据），不要指望已挂载的组件自动降级——半开发半线上的界面比纯线上更危险。

## 反模式

| 反模式 | 为什么错 |
|---|---|
| `if (process.env.NODE_ENV === 'development')` 散落各处 | 判定点不可枚举，切线上靠人肉搜索 |
| 用暗色/浅色当模式 | 主题是外观偏好，模式是信息边界，混在一起两头都不对 |
| 用"是否内网 IP"判模式 | IP 会变、代理会骗；构建期常量才可靠 |
| 线上模式"顺手"保留未登记告警 | 内部质量债暴露给客户，等于自己给自己找投诉 |
| 模式切换不刷新 | 部分组件停在旧数据源，出现"一半能试调一半不能"的怪态 |
| 开发/线上各写一套 Layout | 每加一种形态复制一次，跨页组件丢失、过渡断帧 |

## 验收

- [ ] 全局搜索 `NODE_ENV` / `import.meta.env.DEV` / `process.env.DEBUG`，除 `resolveMode` 外无命中
- [ ] 界面上能看到当前模式，hover 能说出它来自哪里（构建期 / URL / 存储 / 默认）
- [ ] 线上包用 URL 强切 dev：非管理员被拒，管理员切换后角标变黄
- [ ] 线上形态下，未登记告警、源码路径、堆栈全部不可见
- [ ] 刷新与分享链接后，模式形态保持一致

# 和现成方案的边界

装之前先搞清楚：**哪些事别人比我强，什么情况下根本不该装。**

这份文档存在的原因是——如果我不能一句话说清"为什么不用 Storybook / Docusaurus / Notion"，那这个技能就没有存在价值。

## 一张总表

| 方案 | 它最强的地方 | 它覆盖不到什么 | 什么时候选它 |
|---|---|---|---|
| **Storybook** | 组件隔离预览、交互控件、a11y 插件、视觉回归 | 不知道组件**有没有人用**；不管规则 / 接口 / Wiki；和业务应用是两个入口 | 组件库对外发布、要做视觉回归 |
| **Docusaurus / VitePress** | 全文搜索、版本化、SEO、社区主题 | 独立部署后**追不上代码**；不能和应用同屏；规则不能当门禁 | 对外开放的产品文档 |
| **Notion / 飞书文档** | 编辑体验、非技术同学也能写 | 不在仓库里，**不能和 PR 一起 review**；改了什么没人知道 | 产品需求、会议纪要、非代码文档 |
| **Swagger UI / Redoc** | 接口文档的事实标准，可试调 | 只管接口，且常常忘记关线上 | 永远选它，**我不替代，我内嵌** |
| **Backstage** | 企业级服务目录、插件生态 | 重，要专人维护；前端团队单项目用不上 | 几十个服务、有平台团队 |
| **ADR + CONTRIBUTING.md** | 零成本、纯 Markdown | 不能筛选、不能导出 AI 上下文、不能挂门禁 | 3 人以下小项目 |
| **什么都不装，直接读代码** | 最准确 | 换人 / 换 AI 时成本全压在"读代码"上 | **少于 3 人、生命周期少于 3 个月** |

## 逐条说清楚

### vs Storybook：我要的不是预览，是"谁在用"

Storybook 在组件预览上比我强一个档次——它有交互控件（knobs）、能切状态、能跑 a11y 检查。这是它的主场，别跟我这比。

但 Storybook 回答不了这三个问题：

1. 这 30 个组件里，**哪 12 个已经没人引用了**？
2. 新写了一个卡片，**是不是重复实现了已有的那个**？
3. 组件的**准入**由谁守着？（Storybook 里多一个 story 不等于被批准）

我给的是**注册准入门禁 + 使用扫描**：目录里有、注册表没有 → 直接告警；登记了但 0 引用 → 进"待下架"。

两者可以共存：Storybook 做深度预览，控制台做准入与盘点。**别为了统一而砍掉 Storybook。**

### vs Docusaurus：文档站的问题是它活不过三个月

不是没人维护，是**维护它的人看不到代码变更**。文档站一旦独立部署，它就在另一个仓库、另一条流水线、另一个人的待办里。

我的 Wiki 页做的是另一件事：文档和应用**同一个仓库、同一次 PR、同一个屏**。改 `.md` 刷新即生效，不需要重新构建。

代价要说清：我没有全文搜索、没有版本化、没有 SEO。**如果你要做的是对外产品文档，用 Docusaurus，别用我。**

### vs Notion：编辑体验换不来可追溯

Notion 写起来最舒服，这是真的。但"谁在哪个 PR 里改了这条规则"这个问题，它答不上来。

团队里常见的一种半吊子状态：规则在 Notion，代码在 GitLab，两边各写一半，谁都不知道哪边是准的。**要么全搬进仓库，要么承认它只是草稿。**

### vs Swagger：不是竞争，是内嵌

接口文档的唯一正确答案就是代码生成 + 可试调。我只是把它嵌进设置页，顺手解决三个工程问题：同源 iframe 被 `X-Frame-Options: DENY` 拦掉、深浅色不同步、CDN 依赖导致内网打不开。

### 什么时候不该装

诚实一点，以下三种情况别装：

1. **单人项目，生命周期 < 3 个月。** 你自己就是唯一读者，直接读代码更快。
2. **团队没有代码评审习惯。** 门禁的前提是有人在意"未登记组件"，没人在意时脚本只会被 `--no-verify` 跳过。
3. **你只是想要一个好看的后台。** 这个技能不提供 UI 组件，只提供"让内部事实可见"的骨架。

## 同类 agent 技能（2026-10 生态调研）

生态里有几十万个 SKILL.md，但按"管什么"分，头部项目的位置很清晰：

| 技能 | 体量 | 它管什么 | 与本项目的关系 |
|---|---|---|---|
| `pbakaus/impeccable` | ~28K stars / 277K 安装 | AI 前端设计语言：audit / polish / critique / animate 等 21 个命令 | **邻**。它管"好不好看"，我管"项目内部事实是否可访问"。它的 critique 是评审产物，我的组件页是准入名单 |
| `obra/superpowers` | ~192K stars | TDD 驱动的流程铁律（Red-Green-Refactor） | **邻**。它管"怎么写代码"，我管"代码旁边的事实怎么被看见" |
| `johnqtcg/awesome-skills` | 数十个技能 | 技能工程化：设计理由、**定量评估报告**、golden test fixtures | **老师**。它证明了"技能要有可验证的评估"，本项目在此仍有缺口，见下 |
| Anthropic 官方 `anthropics/skills` | 官方 | PDF / DOCX / PPTX / 前端设计 / MCP 构建等 | **不同层**。官方技能做"单点能力"，本项目做"项目基础设施" |

**结论：目前没有直接竞品。** 没有任何技能在做"四件套 + 准入扫描 + 模式可见性"这个组合。

这既是机会也是风险：机会是没人占位，风险是**需求本身没有被验证过**——别人可能根本不觉得自己需要它。

## 已知局限（别急着信）

诚实列出，避免过度承诺：

1. **只有一个来源案例。** 模式提炼自 chaierss 一个真实项目，没有第二个项目、也没有跨栈验证。React / Go 的落地细节是推演，不是实践。
2. **没有量化效果。** 目前说不出"装了之后少了多少重复实现"。真正的证据应该是"34 个组件里 12 个 0 引用，删完少 2800 行"这类数字，本项目还没有。
3. **脚本只做静态匹配。** `console-check.mjs` 的引用扫描对动态 import、字符串拼接注册会漏扫——所以"未使用"只标候选，不给一键删除。
4. **不论证需求。** 如果你从不换人、从不换 AI、项目活不过三个月，这套东西是净成本。

## 一句话总结

**Storybook 管单个组件长什么样，Docusaurus 管对外文档，Swagger 管接口。**
**我管的是它们之间的空白：谁在用、谁该删、规则叫什么、四个入口能不能是同一个。**

那个空白，目前没有现成工具填。

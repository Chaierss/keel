# 设计取舍

这份文档记录**为什么是这样**，以及**哪些方案被否掉了**。改这个项目前先读它，能省掉重新走一遍弯路。

![数据流](assets/architecture.svg)

## 一句话目标

让一个项目里的**内部事实**（规则、组件、接口、文档）只有一个来源，并且这些事实的可见性由模式决定，而不是由谁记得住决定。

## 五条不可协商的约束

1. **零运行时依赖。** 技能要能在只有 Node 的干净容器、内网 CI、离线机器上跑起来。
2. **脚本只读。** 一个会写文件的"体检工具"没人敢装进别人的项目。
3. **不发网络请求。** 没有遥测。被审计时这一条比任何功能都重要。
4. **不绑定栈。** 约束的是「什么算合格」，落地手法按目标框架替换。
5. **`SKILL.md` ≤ 200 行。** 入口文件变长会挤占 agent 的上下文预算，反而降低触发后的执行质量。

## 决策记录

### D1 · 四件套放进设置页，而不是建一个文档站

**否掉的方案**：Docusaurus / VitePress / 自建 docs 站。

否决理由：文档站的问题是**它和代码是两份东西**。多一次部署、多一个仓库、多一个"记得同步"的动作，三个月后一定分叉。

采用方案：四件套是应用里的一个整屏路由页。改代码的同一次 PR 里改 `rules.json`，页面下次刷新就是最新的——**因为页面读的就是那个文件**。

代价：占用了应用的设置页空间，需要项目已经有"设置中枢"这个位置。没有的话，技能第 2 步会先帮你建。

### D2 · 规则存 JSON，不存 TS 常量

参考实现最早把规则写成 `designRules.ts` 里的常量。问题是：

- agent 读不了 TS 常量（要先编译，或者会读到一堆类型断言）；
- 非前端脚本（Python 的后端检查、CI 里的 shell）读不了；
- 页面读的是编译产物，脚本读的是源文件，**两者可能不是同一份内容**。

改成 `rules.json` 之后，页面、脚本、AI 三方读同一份原始字节，这才是"单一真相源"。

### D3 · 组件预览用「同目录 demo 自动发现」，不用巨型 `v-if` switch

**这是参考实现踩过的真实坑。** 它有一个 `ComponentPreview.vue`：

```vue
<Button v-if="key === 'button'" />
<AppTag v-else-if="key === 'app-tag'" />
<!-- …四十个分支之后… -->
```

后果：**新增组件必须回头改这个文件**。于是"注册表"和"预览"是两处要同步，第三个月开始就有一半组件点开是空白。

本项目的做法：注册表里写 `"demo": "auto"`，约定同目录下 `Xxx.demo.vue` 即预览。新增组件只要建两个文件，**不需要动任何中心文件**。

代价：`demo: auto` 找不到文件时会 warn（`COMP-03`）。这是有意的——安静地不显示预览，比报警更糟。

### D4 · 模式只允许一个判定函数

散落读 `process.env.NODE_ENV` 的项目，一定会在某个角落漏一处，而漏掉的往往是**内部事实页**——这正是最不该暴露的那个。

所以模式收敛成一个 `resolveMode()`，加一个常驻角标（防止"我不知道现在是哪个模式"），加一份 `MODE_VISIBILITY` 矩阵（谁能看见什么写在一处）。

`console-check` 的 `MODE-01` 检查这件事是否就位。

### D5 · 扫描器只报「机器能确定错了」的

`console-check` 的分级标准：

- `error` —— 机器能确定：注册表指向的文件不存在、规则 id 重复、清单里的文档不存在。**人可以立刻去修**。
- `warn` —— 需要人判断：组件没有任何引用（可能是刚写好、可能是该删）、文档太短、术语缺 `avoid`。
- `info` —— 只是提示：没检测到 OpenAPI 入口（项目可能压根没后端）。

为什么要这么严：**一个爱刷屏的检查器会被整体关掉**。一旦团队习惯了"红了也不看"，门禁就只剩心理安慰作用。

### D6 · 扫到 0 个文件判 error

原先的实现：目录配错 → 扫到 0 个文件 → 输出"未发现问题" → 退出码 0。

这是最坏的一类失败：**它给你绿灯**。CI 里挂着、每次都是绿的、实际上什么都没扫。所以现在扫 0 个文件直接判 `SEC-00` error，宁可拦住人。

### D7 · 打包用自己的 ZIP 写入器

`Compress-Archive`（Windows）受执行策略影响，`zip`（Linux）在 Windows 上默认没有。为了三个平台一条命令一致，直接按 ZIP 规范写字节：本地文件头 + 中央目录 + EOCD，`deflateRawSync` 压缩，自家 CRC32 表。

顺带的好处：固定 DOS 时间戳后**同样的输入产出逐字节相同的 zip**，发布包可以被校验、被 diff。

代价：约 120 行自己维护的格式代码。有测试守住（解析中央目录、校验条目数、断言根目录是 `SKILL.md`）。

## 已知取舍

| 取舍 | 换来什么 | 失去什么 |
|---|---|---|
| 静态文本扫描，不建 AST | 零依赖、任何语言都能扫、跑得快 | 动态 `import()`、字符串拼接路径会漏；正则误报需要 `.preflightignore` |
| 四件套只读源文件，不做后台索引 | 没有"同步"这一步，永远不会过期 | 不能全文搜索（那是 Docusaurus 的活）；大仓库首屏要读文件 |
| 模板是拷贝而不是脚手架 | 用户能看懂每一行，改起来没有魔法 | 模板升级不会自动同步到已接入的项目（见 `CHANGELOG` 的版本语义） |
| 组件使用检测靠正则 | 跨框架通用 | 别名导入（`import { X as Y }`）会被算成未使用，需要 `manualUsage` 兜底 |

## 考虑过但没做

- **插件系统。** 每个接入栈一个插件听起来很美，实际会让"什么算合格"变成可配置项，而可配置的门禁等于没有门禁。
- **规则的可视化编辑器。** 编辑体验是 Notion 的强项，本项目不竞争。真要编辑，改 JSON 的体验已经够用，而且改错了体检会报。
- **SaaS 版 / 云端同步。** 与"不发网络请求"直接冲突。如果将来做，也必须是完全独立的产品，不能污染技能本体。
- **自动修复（`--fix`）。** 会让"脚本只读"这条承诺失效。宁可输出一条可复制的命令让用户自己执行。
